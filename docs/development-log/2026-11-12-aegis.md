## 2. IAM direction and Phase 0 decisions

A read-only authentication/access-control review identified limitations in the existing authentication model:

- Analyst and approver access used static bearer tokens configured through the environment.
- The static tokens did not provide individually managed user identities, token expiry/revocation or a complete issuance lifecycle.
- The dashboard stored its bearer token in sessionStorage.
- Authentication throttling was process-local at that point.
- HTTPS was an external deployment/reverse-proxy responsibility.
- Security headers and the non-blocking ZAP baseline workflow were also reviewed.

The agreed product direction was **local identity management inside AEGIS**, rather than depending on an external identity provider. The first MFA method selected was **TOTP using authenticator applications**.

The design constraints retained through implementation were:

- Keep the existing analyst/approver role distinction.
- Use stable, immutable internal user identifiers.
- Preserve existing response-audit records, actor references, hash chains, signed checkpoints and signing-key history.
- Use additive, versioned SQLite migrations.
- Never silently migrate the live database during application startup.
- Require explicit operator-controlled migration and verified backup/audit preconditions.
- Keep MFA verification state separate from password authentication.
- Do not trust user-supplied actor IDs, roles or MFA claims.
- Avoid destructive database reset, volume deletion or signing-key replacement.
- Implement and test the IAM foundation in controlled feature branches before integrating public authentication routes.

Phase 0 was a read-only review of existing routes, compatibility boundaries, dashboard authentication, database structure and audit requirements. No source, schema, configuration or runtime changes were made during that inspection.

## 3. Phase 1 — IAM database foundation

### 3.1 PR #10

PR #10 introduced the first local IAM persistence foundation:

- A versioned SQLite migration runner.
- Checksummed migration history and ordered-version validation.
- Transactional savepoint rollback for failed migrations.
- A repository layer with Unicode-aware username normalisation.
- Atomic account/credential record creation with Argon2id-hash-only credential input.
- Explicit migration CLI commands for read-only checking and guarded application.
- Protection against implicit creation of a missing database file.
- Account activation kept behind a controlled workflow.

The initial schema introduced ten IAM tables covering:

1. Migration history.
2. Users.
3. Credentials.
4. MFA factors.
5. Recovery codes.
6. API tokens.
7. Sessions.
8. MFA login challenges.
9. Account activation tokens.
10. IAM security events.

The migration runner is deliberately not invoked automatically at application startup. Applying a migration requires explicit operator attestations for a verified backup, a verified audit-checkpoint inventory and a stopped application. The command refuses to create a missing database implicitly.

## 4. Phase 2A — Password and account lifecycle

### 4.1 PR #11 implementation

PR #11 added local password and account-lifecycle services on an isolated feature branch.

**Password handling**

- Argon2id hashing and verification through argon2-cffi.
- Explicit production profile: 19 MiB memory, two iterations and one lane.
- Password rehash detection and verified rehash generation.
- Passphrase policy: minimum 15 characters and maximum 1,024 UTF-8 bytes.
- No arbitrary composition rules, silent trimming or Unicode normalisation.

**Invitation and activation**

- 256-bit random activation credentials.
- Expiring, single-use activation.
- Public UUID selector for indexed lookup.
- Argon2id hash of the activation secret; plaintext activation secrets are not persisted.
- Activation credentials are displayed once for controlled out-of-band delivery.

**Account controls and audit**

- Password changes require the current password.
- Account disable and lock operations revoke existing IAM sessions.
- Privacy-conscious IAM security-event recording.
- Local operator CLI for invitation, activation, disablement and locking.
- The CLI refuses missing or symlink database paths, checks integrity and migration history, and does not auto-create a database or apply migrations.
- Password and activation-token inputs use hidden prompts.

The CodeQL review identified a weak sensitive-data hashing concern in activation-token handling. The implementation was revised to use Argon2id for the activation secret, with selector-validation tests, rather than persisting plaintext secrets or introducing an unnecessary schema migration.

## 5. Phase 2B — Sessions and browser security

### 5.1 Server-side session primitives

PR #12 added service-level session primitives:

- Opaque 256-bit random session tokens.
- SHA-256 digest-only session persistence; the raw session token is not stored.
- Session issuance restricted to active accounts.
- Password-authenticated sessions begin with MFA not verified.
- Server-side idle and absolute expiry.
- Idle-window renewal that cannot extend beyond absolute expiry.
- Single-session revocation.
- User-wide session revocation.
- Retention cleanup for expired/revoked sessions.

### 5.2 Browser-security primitives

The same PR added:

- Secure __Host- session-cookie helpers.
- HttpOnly and Secure cookie attributes.
- Path=/ and no Domain attribute.
- SameSite=Lax or Strict.
- Bounded cookie lifetime and secure logout-cookie deletion.
- No-store/no-cache response headers.
- Session-bound HMAC-SHA256 CSRF tokens with constant-time verification.
- Exact HTTPS Origin allowlist validation.

### 5.3 Persistent authentication throttling

Additive IAM migration v2 introduced persistent authentication-throttling buckets and a cleanup index.

The implementation includes:

- Atomic SQLite UPSERT-based failure accounting.
- HMAC-only identifiers rather than plaintext usernames/IP identifiers in throttle rows.
- Success reset behaviour.
- Expiry cleanup.
- Privacy-safe threshold audit events.
- Migration history and checksum validation.

Migration v1 remains unchanged. Migration v2 adds the throttling table and its cleanup index.

## 7. Dashboard access-token question and current authentication boundary

The dashboard still uses the existing bearer-token authentication model. Analyst and approver tokens are configured through the deployment environment; the dashboard stores the entered token in sessionStorage.

Consequences:

- Merging Phase 2A/2B does not automatically issue a new dashboard token.
- The current dashboard does not yet provide the new local IAM login flow.
- The token must still be supplied from the configured environment/deployment secret source; it must not be committed to Git, copied into portfolio documentation or printed in terminal logs.
- sessionStorage is browser-session storage, not a permanent identity/session-management system.
- The Phase 2B cookie/session helpers are foundations for a later controlled integration, not proof that the dashboard has migrated away from bearer tokens.

The next authentication integration must preserve analyst/approver separation and must not trust client-supplied identity, role or MFA state.
